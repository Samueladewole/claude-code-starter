# Writing Quality Rules

## When Producing Human-Facing Text

Any time you write prose that a human will read — documentation, explanations, summaries, proposals, PRDs, commit descriptions, PR bodies, UI copy, error messages, onboarding text, or technical writing — apply these skills:

### Universal (apply to all writing)

1. **`clear-writing`** — Reader-first thinking: lead with the point, use topic sentences, avoid the Curse of Knowledge, edit ruthlessly
2. **`writing-clearly-and-concisely`** — Strunk's composition rules: active voice, positive form, concrete language, omit needless words
3. **`copy-editing`** — Grammar, consistency, proofreading

### Context-Specific (apply when matched)

4. **`sticky-ideas`** — When writing needs to be remembered or acted on (pitches, summaries, proposals, PRDs): apply the SUCCESs checklist (Simple, Unexpected, Concrete, Credible, Emotional, Stories)
5. **Security / risk writing** — When writing threat assessments or risk reports for technical leaders: be authoritative and precise. Open with concrete incidents, give evidence, close with the implication. Measured, never alarmist.
6. **`workshop-facilitation`** — When structuring tutorials, onboarding, presentations, or any learning experience: use the Workshop Skeleton, alternate teaching formats, define measurable outcomes
7. **`professional-communication`** — When writing emails, Slack messages, meeting agendas, or status updates: use What-Why-How structure, audience calibration
8. **`copywriting`** — When writing marketing copy, landing pages, product descriptions, or sales content

## Always

- Lead with the conclusion, not the background
- One idea per paragraph, with a topic sentence
- Concrete language over abstract ("pages load in 200ms" not "improved performance")
- Cut filler words: "in order to" → "to", "at this point in time" → "now", "due to the fact that" → "because"
- Active voice over passive ("the server rejects the request" not "the request is rejected")
- If it can be misunderstood, rewrite it
- Match voice to context: intelligence briefings are dark and tactical; product docs are clear and direct; proposals need to stick
- Write classic prose as the standard: clean sentences built on commas, semicolons, colons and full stops. This is the default register, not a special case

## Never

- Wall-of-text paragraphs without structure
- Hedging everything with "it might be possible that..."
- AI slop: "delve", "leverage", "robust", "seamless", "cutting-edge", "tapestry", "holistic", "game-changing"
- Over-relying on the em dash (—). It's an AI tell, and the opposite of classic prose. Classic writing is the standard; the em dash is an occasional tool used only where it is genuinely necessary, never a default rhythm. Prefer commas, semicolons, colons, full stops; at most one em dash per short message, and often none. Mind semicolon correctness: it joins two independent clauses, use a comma for a subordinate result clause
- Starting with context/background instead of the point
- Writing for yourself instead of the reader
- Generic openings ("In today's threat landscape...", "In the ever-evolving world of...")
- Sensationalism in security writing — be measured, not alarmist
